# infra — AI Agent Reference

This is a config-driven infra repo that builds, previews, and deploys a multi-service stack
(frontends + backends + datastores) behind one nginx edge, driven entirely by
[`config/stack.yaml`](./config/stack.yaml). This file is the exhaustive command/architecture
reference for an AI agent working directly in this repo. For narrative human-facing walkthroughs,
see [`readme/`](./readme/README.md) — `readme/MASTER_GUIDE.md` and `readme/PROD_RUNBOOK.md` are the
canonical deep-dive docs; this file exists so an agent doesn't have to read all of them to act.

If you are an AI agent working in a **different** repo (a service repo that this infra deploys) and
just need to know how to integrate with this infra, skip to
["For AI Agents Calling In From Another Repo"](#for-ai-agents-calling-in-from-another-repo) below.

## Source of Truth

`config/stack.yaml` defines everything: `sources` (git repos), `services` (build/deploy config per
service), `ingress` (hostname routing), `groups` (shared-node process groups), `tls.root_domains`
(cert config). Nothing else should be hand-edited to add/change a service — always edit
`stack.yaml`, then run `npm run validate`.

Everything under `generated/` is build output — never hand-edit it, it's regenerated by the
build/render/publish scripts.

## Service Modes

A service's `deploy.mode` determines how it runs:

| Mode | What it means | Example |
|---|---|---|
| `edge-static` | Static build output served directly by the nginx edge container | `portfolio-web`, `municipal-admin` |
| `isolated` | Runs in its own container | `subsnepal-api`, `subsnepal-web` |
| `shared-node` | Runs as a PM2 process inside a shared Node container (`deploy.group` picks which group) | `cors-api`, `getdata`, `municipal-api` |
| `image` | Prebuilt image, no source repo/build, `kind: datastore` | `redis` |

`build.strategy: dockerfile` (only valid with `deploy.mode: isolated` + `kind: backend`) builds the
service's own `Dockerfile` instead of generating a Node image — for non-Node runtimes (e.g. `otp-api`
is Spring Boot).

Full walkthroughs for adding/moving/removing a service: [`readme/SERVICE_MANAGEMENT.md`](./readme/SERVICE_MANAGEMENT.md).

### Validation rules enforced by `npm run validate` (`scripts/validate/checks/*.mjs`)

- `source-schema.mjs` — every source has a valid repo URL + ref; every non-image service has `source.key`
- `service-modes.mjs` — image-mode services define `image` and must not define `source.key`/`build`/`runtime.start`; `build.strategy: dockerfile` requires `deploy.mode: isolated` + `kind: backend`; `depends_on` targets must exist and be enabled, and is only valid on `isolated`/`image` services; `resources` only honored on `isolated`/`image`
- `service-refs.mjs` — `ingress[].upstream.service` and `routes[].service` point at real, enabled services
- `required-env.mjs` — every key in a service's `env.required` is present in its merged env
- `env-files.mjs`, `duplicate-hosts.mjs`, `groups.mjs`, `hostname-lint.mjs`, `ports.mjs`, `route-conflicts.mjs`, `source-remote.mjs` — structural/naming/port-conflict checks
- `--remote` (`npm run validate:remote`) additionally checks that each source's `repo`+`ref` is actually reachable

## Env Files

- `env/global.env`, `env/global.secrets.env` — applied to every service
- `env/services/<name>.env` — per-service non-secret values
- `env/services-secrets/<name>.env` — per-service secret values
- Merge order/precedence: `scripts/lib/env-merge.mjs`

Env values are managed via **Infisical** (root path `/`), pulled locally per environment:

```bash
npm run infisical:login
npm run infisical:init
npm run infisical:pull:development        # writes env/global*.env + env/services*/*.env
npm run infisical:pull:staging
npm run infisical:pull:production
npm run infisical:pull:development -- --only=<service>   # scope to one service
```

`.env` at repo root is a separate, local-only file (not Infisical-managed) — it currently holds
`SERVER=user@host`, the deploy target read by `scripts/server/deploy.sh`.

## Full Command Reference

### Validate

```bash
npm run validate            # local structural validation
npm run validate:remote     # + check source repos/refs are reachable
```

### Build

```bash
npm run build:edge-static [-- --service <name>]
npm run build:isolated-preview [-- --service <name>]
npm run build:shared-node-preview
# each has a :stub variant that skips real builds (fast structural test)
```

### Preview (disposable local runtime per mode)

```bash
npm run preview:edge-static:render|up|down     # port 8088
npm run preview:isolated:render|up|down        # port 8089
npm run preview:shared-node:render|up|down     # port 8090
```

### Render (compose.yaml / nginx.conf from stack.yaml, no build)

```bash
npm run render
```

### Release (integrated local runtime, port 8091 by default)

```bash
npm run release:publish -- --release <id> [--port 8091]
npm run release:apply -- --release <id>
npm run release:rollback [-- --release <id>]   # omit --release: newest release that isn't current
```

### Production Release (TLS, port 80/443)

```bash
npm run release:publish:prod -- --release <id>              # or release:publish:prod:registry to push images to a registry (bsingh6636)
./scripts/server/push-release.sh <id> user@server-ip         # package, upload, run deploy-on-server.sh remotely
```

One-command shortcuts (prefer these unless you need to inspect an intermediate release):

```bash
npm run server:ship [-- <server>]     # publish (auto-generated UTC-timestamp release id) + push + deploy in one shot; server defaults to SSH alias `aws`
npm run server:deploy [-- <release-id>]   # package + deploy an *already published* release (defaults to latest); server read from SERVER in .env
```

Server-side rollback (script must be copied up first — it is not persisted on the server):

```bash
scp scripts/server/rollback-on-server.sh user@server-ip:/tmp/
ssh user@server-ip "sudo bash /tmp/rollback-on-server.sh <release-id>"
```

`server:bootstrap` (`npm run server:bootstrap`) provisions a fresh server via `bootstrap-server.sh` — one-time setup, not a routine deploy step.

### SSL

```bash
npm run ssl:generate-domains[:dry]     # regenerate ssl-setup/domains.conf from stack.yaml
npm run ssl:certbot:grouped            # one cert per root domain (recommended for prod)
npm run ssl:certbot                    # one cert per hostname
npm run ssl:certbot:dry
npm run ssl:certbot:force-all
sudo bash ssl-setup/certbot-run.sh --domain <domain>   # single domain
sudo bash ssl-setup/ensure-fallback-cert.sh            # self-signed fallback so nginx starts even with missing certs; run before `docker compose up` on server
```

## Deploy Target

Production runs on AWS EC2. `.env`'s `SERVER=ubuntu@<ip>` and the SSH config alias `aws` both point
at it — there is no GCP/Azure infra despite what any doc predating this note might say. Server-side
layout: `/opt/brijesh-infra/{releases,current,data,incoming}` — `current` is a symlink to the active
release directory, flipped atomically by `deploy-on-server.sh`.

Known dead config: `config/stack.yaml`'s `project.live_symlink` key
(`/opt/brijesh-infra/live/current`) is parsed by `scripts/lib/normalize-stack.mjs` but never
consumed anywhere — the actual symlink path is hardcoded as `/opt/brijesh-infra/current` in
`scripts/server/deploy-on-server.sh`. Trust the hardcoded path, not the config key, until this is
reconciled.

## For AI Agents Calling In From Another Repo

If you're an agent working inside a sibling service repo (e.g. one that gets deployed by this infra,
checked out alongside it so this repo is reachable at `../infra`), here's the minimal contract:

- **You do not deploy from the service repo.** Deploys are triggered from `../infra` — you register
  the service in `../infra/config/stack.yaml` and someone runs `npm run validate` + a release/deploy
  command from there.
- **To get a new service deployed**, from `../infra`:
  1. Add a `sources.<key>` entry pointing at your repo + ref.
  2. Add a `services.<name>` entry (pick the right `deploy.mode` — see [Service Modes](#service-modes)).
     If your service is not plain Node.js, use `build.strategy: dockerfile` and provide a `Dockerfile`
     at your repo's context root that listens on `runtime.port` and takes config via env vars at
     **runtime**, not build time.
  3. Add env files: `../infra/env/services/<name>.env` (non-secret) and
     `../infra/env/services-secrets/<name>.env` (secret) — list required keys under `env.required` in
     the service entry.
  4. Add an `ingress` entry if the service needs a hostname.
  5. Run `npm run validate` in `../infra`.
- **Your repo owns**: application code, its own `Dockerfile` if using `build.strategy: dockerfile`,
  and documenting what env vars it needs.
- **This repo owns**: which env vars actually get injected, TLS, routing/hostnames, process
  supervision (PM2 for shared-node, container lifecycle for isolated), release snapshots, and rollback.
- Full detail: [`readme/SERVICE_MANAGEMENT.md`](./readme/SERVICE_MANAGEMENT.md) (add/move/remove a
  service) and [`readme/MASTER_GUIDE.md`](./readme/MASTER_GUIDE.md) (full operator workflow).
